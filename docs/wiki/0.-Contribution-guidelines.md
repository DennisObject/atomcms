# Contributing to Atom CMS

Thank you for helping. Keep each pull request small: one feature, one fix or one refactor.

## Start a change

Start from the latest `dev` branch. Open your pull request against `dev`.

```bash
git switch dev
git pull --ff-only origin dev
git switch -c bugfix/descriptive-change
```

Name your branch by intent:

- `feature/<descriptive-kebab-case>` for new features
- `bugfix/<descriptive-kebab-case>` for fixes
- `refactor/<descriptive-kebab-case>` for cleanups without new behavior

Use Conventional Commit messages. The pull request title must be conventional and at most 70 characters.

The pull request body has a `## Why` section with one or two short sentences: the reason and the new behavior. Add a `## Testing` section only when a reviewer must test by hand. Then list the commands, routes, actions and expected results. Automated results belong in CI.

## Write the code

- Follow the repository's agent instructions and the Laravel Boost guidance. Use the [Laravel 13 documentation](https://laravel.com/docs/13.x).
- Extend the controllers, Form Requests, policies, services and emulator contracts that already own the behavior.
- Keep the supported themes, languages, clients and emulators working.
- Register things where the app already does: `bootstrap/app.php`, `app/Http/Kernel.php`, `app/Console/Kernel.php` and `config/app.php`. Newer Laravel examples may show a different layout.
- Use `config()` in app code. Read environment variables only in config files, so config caching works.

## Laravel Boost

1. Set `APP_ENV=local` in your development `.env`.
2. After you install dependencies or update framework packages, run `php artisan boost:update`. Review the changes.
3. Run `php artisan boost:install` to set up your agent, MCP connection and skills.

See [Laravel Boost](https://laravel.com/docs/13.x/boost).

## Run the checks

```bash
composer install
npm ci
composer lint
composer analyse
composer test
npm run build:atom
npm run build:dusk
```

Run focused tests for your change first. Run both emulator suites (Arcturus and Ada) when you change shared models, the database, permissions or payments. Also try the changed flow in a browser or on the command line. A successful build does not prove the code works.

The tests need two throwaway MariaDB databases: `testing` and `testing_ada`. They drop and recreate tables.

- Use database credentials that can only reach these two databases.
- Check `phpunit.xml`.
- Clear the config cache before you test.
- Never point the tests at a hotel database.

The Arcturus and Ada test schemas load by themselves. See the [test schema notes](../../database/schema/README.md).

## Update the docs

Change the matching pages in `docs/wiki/` in the same pull request. A maintainer publishes the reviewed pages to the GitHub wiki after the merge.
